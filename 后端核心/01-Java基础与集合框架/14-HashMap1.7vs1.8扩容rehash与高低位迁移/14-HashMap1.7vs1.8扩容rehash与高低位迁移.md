## 二、做什么  
  
### 2.1 引入红黑树的原因  
  
极端 hash 冲突（如恶意构造相同 hashCode 的 key）时链表退化为 O(n)，红黑树保证最坏 O(log n) 的查询。  
  
### 2.2 为什么树化阈值是 8  
  
负载因子 0.75 下，桶内链表长度达到 8 的概率约千万分之六（泊松分布），正常数据几乎不可能触发，红黑树只在极端场景兜底。  
能用泊松分布，是因为桶内元素数本质是二项分布 B(n, 1/m)，而 HashMap 天然满足 n 大、p 小、np≈0.5 为常数这三个条件，正好落在泊松近似的适用范围里。前提是 hash 均匀——一旦被恶意构造，假设失效，那正是树化要兜底的极端场景。  
  
### 2.3 为什么退化阈值是 6 而不是 7  
  
避免链表与树在长度 7/8 边界频繁互相转换造成抖动  
  
### 2.4 为什么最小树化容量是 64  
  
数组长度 <64 时先扩容（rehash 会打散冲突），而不是直接树化  
当数组容量很小时，链表过长的根本原因是数组太短，而不是 hash 冲突太严重。这种情况下扩容是更对症、成本更低的解决方案  
  
### 2.5 为什么不直接用红黑树  
  
+ TreeNode 是普通 Node 的两倍内存  
+ 插入/删除需要旋转维护平衡  
+ 链表在长度小时（<8）遍历更快。  
+ 树化的概率本身就低

**1. 阈值8/6/64的由来(含泊松分布)**

为什么不是7或者8这是为了留出缓冲空间，避免树和链表之间的频繁转换
