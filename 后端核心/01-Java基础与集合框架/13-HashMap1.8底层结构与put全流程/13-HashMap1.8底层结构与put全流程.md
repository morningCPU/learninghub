## 二、做什么  
  
### 2.1 基础知识  
  
看 JavaGuide "HashMap 源码分析（JDK1.8）" + 小林coding（xiaolincoding.com）"图解 HashMap"；黑马 Java 基础"集合"章节的 HashMap 视频 1.5 倍速补充。  
  
**1. 基础定义**  
HashMap实现Map接口，键唯一，值可重复，线程不安全  
底层是哈希表，平均查找O(1)  
底层结构：数组+链表+红黑树  
  
>数组：哈希桶bucket,存放桶头节点  
>链表：拉链法解决哈希冲突，节点Node<K,V>,包含hash,key,value,next  
>红黑树：链表过长时升级为TreeNode,查找O(logn)  
  
**2. 核心常量**  
  
```java  
static final int DEFAULT_INTIAL_CAPACITY = 1 << 4; //默认初始容量16  
static final int MAXIMUM_CAPACITY = 1 << 30; //最大容量  
static final float DEFAULT_LOAD_FACTOR = 0.75f; //默认负载因子  
static final int TREEIFY_THRESHOLD = 8; //链表树化阈值，链表长度>=8  
static final int UNTREEIFY_THRESHOLD = 6; //树退化成链表阈值，节点<=6,这个节点指的是链表中的节点  
static final int MIN_TREEIFY_CAPACITY = 64; //树化前提,table数组容量>=64，就是桶的数量>=64  
```  
  
> 会先判断一个桶中节点的数量是否>=8  
> 如果是  
> 	还需要判断桶的数量是否>=64，是才对这个桶进行树化，不是看是否需要扩容  
> 不是  
> 	看是否需要扩容  
  
+ 扩容因子0.75是时间与空间的折中，太小浪费空间，太大冲突变多，查询变慢  
  
**3. hash扰动函数与桶索引计算**  
  
```java  
//扰动函数  
static final int hash(Object eky){  
    int h;  
    return (key == null) ? 0 : (h = key.hashCode())^(h>>>16);  
}  
```  
  
+ `>>>` : 这个是无符号右移，把hashCode高16位无符号右移到低16位  
+ `^` : 异或，将高低16位混合，让高位信息参与到低位运算，减少哈希碰撞  
+ key可以为null，会放在0号桶  
  
```java  
//桶索引计算  
index = hash & (table.lenght-1);  
```  
  
+ 只有数组长度是2的n次方时，`hash&(n-1) == hash%n`，位运算比取模更快  
+ HashMap容量强制为2的幂  
  
**4. put()流程**  
方法入口 `put(k,v)`  
内部调用 `putVal(hash(key),key,value,false,true)`  
  
> 1. 判断table数组是否为null或者长度为0，调用resize初始化数组  
>    这里会进行懒加载，只有第一次put才会初始化table  
> 2. 计算hash，算出桶下标  
> 3. 插入会判断桶头节点类型，判断是链表(尾插法)还是红黑树  
> 4. 会先判断是否进行树化  
> 5. 插入成功后判断是否进行扩容  
  
**5. resize()扩容机制**  
新容量 = 旧容量 * 2  
新阈值 = 新容量 * 0.75  
  
> 1. 新建Node数组进行迁移  
> 2. 因为扩容为了两倍，所以不需要全部重新计算hash，两倍看成二进制就是前面多了个1(011->111)  
>    用旧桶中节点hash&旧容量，高位结果0新数组下标不变，结果1下标=旧下标+旧容量  
  
迁移时保持链表原有顺序(尾插法)，不会产生环形链表，解决了jdk1.7多线程扩容死循环的问题  
  
+ **树化节点个数>=8但是退化节点个数<=6的原因**  
  留缓冲空间，防止扩容/删除时在链表、红黑树之间频繁来回切换  
  
+ **为什么用红黑树不用AVL树**  
  AVL树的平衡更加严格，旋转代价大  
  红黑树平衡更加宽松，插入删除旋转更少  
  
**6. get()流程**  
`get(key)`  
调用getNode  
  
> key为null，取0号桶，否则计算hash,先找到桶，再在桶中找  
  
  
  
## 三、实践  
  
**1. 写出put流程伪代码**  
  
```text  
1. 判断table数组是否为空或者长度为0，进行懒加载，在有第一个put的时候才进行初始化  
2. 计算插入节点key的hash,看放入哪一个桶  
3. 桶为空则创建链表节点直接放入，不为空则判断桶头节点类型，判断是进行链表的操作还是进行红黑树的操作进行跟新或插入，插入后看是否扩容或者树化  
4. size++,看是否需要扩容  
```  
  
**2. 解释 (n-1)&hash为什么等价取模并且更快**  
  
`(n-1)^hash == hash%n`  
n会被固定为2的幂，也就是 `n=2^k`  
写为2进制就是 `1000...` , 只有最高位是1，其他k位都是0  
那么 `n-1` 机会变为 `0111...`,只有最高位是0，其他k位都是1  
这个时候通过 `&` 与运算就会只保留低k位，这与 `hash%2^k`也就是`hash%n`的含义是一样的  
`%n`的取值范围是`0~n-1`这正好可以通过`^`实现  
  
取模的CPU底层是除法运算，开销更大。CPU时钟周期更长  
与运算是简单逻辑运算，单周期完成更加简单  
  
  
  
## 四、问题  
  
**1. HashMap put的完整流程**  
  
```text  
1. 判断table数组是否为空或者长度为0，进行懒加载，在有第一个put的时候才进行初始化  
2. 计算插入节点key的hash,看放入哪一个桶  
3. 桶为空则创建链表节点直接放入，不为空则判断桶头节点类型，判断是进行链表的操作还是进行红黑树的操作进行跟新或插入，插入后看是否扩容或者树化  
4. size++,看是否需要扩容  
```  
  
**2. 为什么用 (n-1)&hash 而不是取模**  
  
取模的CPU底层是除法运算，开销更大。CPU时钟周期更长  
与运算是简单逻辑运算，单周期完成更加简单  
  
**3. 负载因子为什么是0.75**  
  
是空间开销和哈希冲突概率的折中，小了空间开销太大，大了哈希冲突更加频繁查找效率低  
理论依据是泊松分布，hash均匀的情况下单个桶链表长度达到8的概率非常小
