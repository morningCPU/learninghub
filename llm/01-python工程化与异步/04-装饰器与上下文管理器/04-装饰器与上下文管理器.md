# 04-装饰器与上下文管理器  
  
## 作用  
  
真实项目的代码复杂度很大的一部分来自非功能性需求，比如日志、监控、并发控制等等。  
装饰器和上下文管理器就能够把这类逻辑集中到一处定义，并且能够在多处声明式使用，让业务函数只保留纯粹的做什么  
  
  
  
## 一、学什么  
  
> 1. 装饰器原理：闭包+functools.wraps  
> 2. 上下文管理协议：enter、exit、contextlib.contextmanager  
> 3. 可重入问题  
  
  
  
## 二、基础知识  
  
### 2.1 装饰器的本质  
  
**装饰器的本质就是一个语法糖**  
`@decorator` 等价于 `func = decotator(func)`  
**带参数的装饰器就是装饰器工厂**  
`@decorator(a=1)` 等价于 `func = decorator(a=1)(func)`  
**主要就是两层：**  
工厂层用于接收参数  
包装层用于接收被装饰函数，并返回闭包(wrapper)  
  
> 闭包要配合 functools.wraps 使用  
> 把原函数的元数据拷贝到wrapper上  
> 如果不使用 @wraps(func),wrapper就会覆盖 `__name__`,`__doc__`,`__module__`这些元信息  
>  
> 导致debug，异常栈，help文档等出错  
  
**多个装饰器可以叠加使用**  
  
```python  
@A  
@B  
@C  
def func():pass  
# 等价于 A(B(C(func))  
```  
  
从上到下包装，从下到上执行  
  
### 2.2 上下文管理协议  
  
**(1) 上下文管理器的两套写法**  
**1.原生协议写法**  
类+`__enter__`+`__exit__`  
标准协议、最底层  
**2. @contextlib.contextmanager**  
装饰器+生成器  
简化的语法糖，底层还是要转化为第一种  
  
**(2) 原生协议**  
  
**1. 执行顺序**  
  
```python  
with obj as val:  
    ...  
```  
  
执行步骤：  
  
> 1. `obj.__enter__()`调用  
> 2. `__enter__()` 返回的值赋值给 `as` 后面的 `val`  
> 3. 运行 `with` 里面的代码块  
> 4. 最后不管是不是正常结束都会执行`__exit__(exc_type,exc_val,exc_tb)`  
  
**2. `__exit__`的三个参数**  
  
1.`exc_type` : 异常类型  
2.`exc_val` : 异常实例  
3.`exc_tb` : traceback对象，保存异常堆栈信息  
  
> exit 的返回值决定异常要不要继续向外抛  
> return True : 吃掉异常  
> return False / 不写return : 外抛  
  
**(3) contextlib.contextmanager**  
生成器简化写法  
本质是装饰器帮忙自动包装成一个满足上下文协议的类  
  
```python  
from contextlib import contextmanager  
  
@contextmanager  
def my_ctx():  
    # -------- yield 之前的代码  == __enter__ 里面的逻辑  
    print("准备进入")  
    yield "给as的值"   # yield 的值就是 as 拿到的 val  
    # -------- yield 之后的代码  == __exit__ 里面的逻辑  
    print("准备退出，清理资源")  
```  
  
### 2.3 可重入问题  
  
可重入上下文管理器：同一个实例，能不能嵌套多次with  
  
```python  
# 可重入就是下面这种写法能不能正常跑  
ctx = MyCtx()  
with ctx:  
    print("第一层")  
    with ctx:  
        print("第二层")  
```  
  
默认 @contextmanager 生成器版本不可重入  
因为生成器对象只能迭代一次  
第一次进入 with：跑生成器到 yield，暂停。  
退出第一层 with：跑到生成器函数末尾，生成器**耗尽**。  
第二次再进入 with，尝试迭代已经跑完的生成器，直接 `StopIteration` 报错。  
注意区分下面这个：  
  
```python  
# 这个没问题：每次 with 都调用函数，新建一个全新生成器实例  
with lock():  
    with lock():  
        pass  
```  
  
**如何实现一个可重入上下文管理器呢**  
可以使用计数方案  
自己维护一个引用计数，第一次进入的时候才拿资源，嵌套进入只计数。全部退出（计数归零）才释放资源。  
  
```python  
class ReentrantLock:  
    def __init__(self):  
        self.count = 0  # 重入计数器  
  
    def __enter__(self):  
        if self.count == 0:  
            print("真正获取锁")  
        self.count += 1  
        return self  
  
    def __exit__(self, exc_type, exc_val, exc_tb):  
        self.count -= 1  
        if self.count == 0:  
            print("真正释放锁")  
        return False  
  
lock = ReentrantLock()  
with lock:  
    print("第一层")  
    with lock:  
        print("第二层")  
print("结束")  
```  
  
  
  
## 三、实践  
  
```python  
def timed(func:Optional[Callable]=None):  
    def decorator(fn:Callable):  
        @wraps(fn)  
        def wrapper(*args, **kwargs):  
            start = time.perf_counter()  
            try:  
                res = fn(*args, **kwargs)  
                return res  
            finally:  
                cost = time.perf_counter() - start  
                logging.info(  
                    dict(  
                        action="func_timed",  
                        func_name=fn.__name__,  
                        cost_ms=round(cost * 1000,2)  
                    )  
                )  
        return wrapper  
    if func is None:  
        return decorator  
    else:  
        return decorator(func)  
```  
  
  
  
## 四、问题  
  
**1. 多个装饰器叠加，谁先执行**  
  
最上面装饰器先进入，最后执行原函数  
  
**2. @wraps 不加会坏什么**  
  
元数据丢失  
  
**3. 重试装饰器怎么保证不会重试到不可重试的错误**  
  
维护可重试异常白名单；只有白名单内异常才 sleep 重试；其余异常直接抛出，不进入重试循环。生产还可以加重试最大总耗时、重试熔断。
